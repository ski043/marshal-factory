# Operating marshal-factory

Reference for how each part of the factory behaves once it is installed. For installing it, see the [README](../README.md).

## Parts

- **Wire a target repo.** `bun scripts/install-target.ts <repo>` adds the reporter hooks, the `factory-report` MCP server and `.agents/playbooks/factory.md`, all pointing at this checkout. Re-running changes nothing. Commit the result in the target repo.
- **Playbook.** The factory playbook ships with the factory, not with the target repo, so an onboarded repo needs no copy. Every launch message ends with a **Factory playbook** section naming its absolute path where the thread runs: `/opt/marshal-factory/playbooks/factory.md` in a sandbox (the image build copies `playbooks/factory.md` and `playbooks/onboarding.md` there), `<runner checkout>/playbooks/factory.md` for a local thread (`lib/playbook.ts`). When the repo's main also has `.agents/playbooks/factory.md` (a repo wired with install-target), the section says the factory's playbook is authoritative and the repo copy only adds notes about that repo. Conflict send-backs, answers to a question and watchdog nudges name the same path. The playbook extends PStack's bundled playbooks as a project playbook would; PStack is in the image and on the runner Mac, and `factory-verify` is on `PATH` in a sandbox and named by the `report_stage` reply elsewhere, so nothing it points at depends on the repo.
- **GitHub App.** The runner reads PRs as the GitHub App named in the manifest in `scripts/setup-github-app.ts`, not as a `gh` login. `bun scripts/setup-github-app.ts` opens a local page that sends the app manifest to GitHub. Click **Create GitHub App**, then pick the repos the factory works in and click **Install**. The script stores the app id, key and webhook secret in `~/.config/marshal-factory/github-app.json` with mode 600, and records the installation. `lib/github/app.ts` mints a one-hour installation token per repo from that file and reuses it until five minutes before it expires; `lib/github/pulls.ts` reads, comments on and merges PRs with it, and a post-merge revert pushes with it ([Merge decisions](#merge-decisions)). T3 threads still push and open PRs with the user's own `gh` and git credentials.
- **Webhooks.** `bun scripts/install-webhooks.ts` creates the Linear webhook (team FAC, Issue and Comment), pointing at the ingest Function, and records its id under `factory.webhooks`. GitHub deliveries (`pull_request`, `pull_request_review`, `push`, `issues`) come from the GitHub App's webhook, which the manifest points at the `main` Function. The Function checks the signatures (`Linear-Signature` with a webhookTimestamp no older than a minute, `X-Hub-Signature-256` with the app's webhook secret), stores every delivery under its delivery id so a redelivery does nothing, and records an intent: claim, stop, answer, merged, recheck_conflicts or request_changes ([Needs you inbox](#needs-you-inbox)). Other GitHub events, such as `installation` or `issues`, are stored with no intent. The Linear and ingest secrets live in `.env.local`; `neon.ts` reads the app's webhook secret from `GITHUB_APP_WEBHOOK_SECRET` or else from `github-app.json`, so `neon deploy --env .env.local --no-env-pull` fails until the app exists. That deploy only adds Function env vars that are missing: it keeps a value already set, even when `neon.ts` now gives another, and keeps a name `neon.ts` no longer lists. To change a value, such as a rotated secret, run `neon functions deploy ingest --src functions/ingest/index.ts --env NAME=VALUE`, and check the names with `neon functions get ingest -E`, which lists names only. Set `FACTORY_TEAM_KEY` and `FACTORY_LABEL` there too when the config uses another team or label.
- **Runner.** `runner/index.ts` is the only process that touches T3, git and the GitHub API. It subscribes to open intents and to issues with an unsynced stage through Neon Realtime and acts through `runner/ops.ts`. It claims and launches (`t3 thread start --worktree origin/main` after a fetch, and logs whether the worktree really sits on origin/main), stops, resumes on an answer, writes merges back and rechecks conflicts after a push to main. Every `tickSeconds` (90) a plain timer claims into free slots, checks open PRs for merges and conflicts, and runs the watchdog, usage reconcile and write-back, with cleanup hourly. On startup it reconciles everything a missed webhook could have changed, so downtime only delays work. `bun scripts/install-runner.ts` installs it as the LaunchAgent `com.marshal-factory.runner` (restarts on exit, log `~/Library/Logs/marshal-factory/runner.log`); `--uninstall` unloads it. `bun runner/index.ts --once` runs one reconcile by hand.
- **Write-back.** Stage `pr` moves the Linear issue to In Review with the PR link, `waiting` posts the question, and a merged PR moves it to Done. `failed` posts the reason, moves the issue back to Todo, and swaps the `factory` label for `factory-failed`, so the runner does not pick it up again in a loop.
- **Retry.** Adding `factory` back to a failed issue claims it again as a new attempt on its own branch (`factory/FAC-7-a2`) and the card shows the attempt, its spend, and the total of all attempts. Comment ids are derived from the stage event, so a replay never posts twice.
- **Config.** `~/.config/marshal-factory/config.json` holds `ingestUrl`, `secret` and `linearApiKey`. An optional `factory` object overrides the limits in `lib/config.ts`: `teamKey`, `label`, `maxInFlight` (4), `stuckAfterMinutes` (30), `stoppedGraceMinutes` (2), `failAfterNudgeMinutes` (30), `pricing` (per-model prices over the defaults; see [Merge decisions](#merge-decisions)), `cleanupGraceDays` (3), `subagentIdleHours` (6), `tickSeconds` (90), `inventoryMinutes` (10), `postMergeWatchMinutes` (60), `noCiGraceMinutes` (5; see [Merge decisions](#merge-decisions)), `stop` (`checkSeconds` 15, `settleSeconds` 30, `interruptAfterSeconds` 60, `giveUpAfterMinutes` 5; see [Stopping a job](#stopping-a-job)), `machineId`, `t3StatePath`, `provider` and `model` for new threads when the panel's Settings page has none saved, `repos`, which the installer fills, `webhooks`, which install-webhooks fills, and `sandbox`, the Modal limits described [below](#running-jobs-in-modal-sandboxes). An old `budgetUsd` key is ignored. The GitHub App lives in `~/.config/marshal-factory/github-app.json` (`MARSHAL_FACTORY_GITHUB_APP` overrides the path).
- **Machines.** Each runner reports its Mac in the `machines` table, keyed by the Mac's `IOPlatformUUID` (`factory.machineId` overrides it, so a test runner keeps its own row). On every tick, from its own timer outside the serial queue, it writes a heartbeat with CPU load, memory in use, free disk and in-flight against max capacity. A collector that fails reports `unknown` for its field and never skips the beat. At startup and every `inventoryMinutes` (10) it also collects the runner commit, whether T3 is up and its version and environment id, the T3 Connect state, the T3 projects, the `origin` of each factory repo, and the T3 provider instances (harnesses) with their current models, read from T3's `settings.json` and `model-manifest.json`. The inventory is written only when it differs from the last one written. T3 projects come from T3's state database, opened read-only (`factory.t3StatePath`, default `$T3CODE_HOME/userdata/statev2.sqlite`). When that fails, the runner runs `t3 thread list --project <repo>` for each factory repo, and when every probe fails the field is `unknown`. Jobs record the machine that launched them in `jobs.machine_id`.
- **Cleanup.** The runner walks the `factory/*` branches, worktrees and T3 threads of every repo in `factory.repos`. A merged issue's worktree and local branch go right away, and a failed one's after `cleanupGraceDays`. Anything with uncommitted files, commits no remote holds (unless the PR merged that exact head), or a running thread is held and listed under `cleaned.held`. Idle Claude Code subagent worktrees under `<repo>/.claude/worktrees/` go the same way, with commits no remote has pushed to `factory-salvage/<branch>` first. The `t3` CLI cannot archive threads, so the runner lists the threads left behind under `cleaned.archive` in its log; archive them in T3 by hand or from an agent with `t3_thread_organize`.
- **Spend.** The factory measures what each attempt spends, main sessions plus subagents, and never caps it. On factory branches the reporter sends a usage snapshot at most every 30 s mid-turn, so the card's spend stays close to real time. Ingest still answers every batch with the spend of the branches it touched, for reporters from before the cap was removed. `hooks/budget.ts` is a no-op that allows every tool call, kept because repos wired before then still name it; re-running install-target drops it from their `.claude/settings.json`. The `jobs.budget_usd` column is unused and keeps a default of 5 for runners and ingest deployed before then.
- **Merge conflicts.** A push to main makes the runner wait for GitHub to recompute mergeability, then read every open factory PR through the GitHub App. When a PR in stage `pr` turns conflicting, its thread is told to merge `origin/main`, resolve, rerun checks and report `pr` again, and the run moves back to Implementing. This happens once per PR head.
- **Watchdog.** The runner's timer checks issues in a working stage. One that has been quiet for `stuckAfterMinutes`, or whose thread stopped and stayed quiet for `stoppedGraceMinutes`, gets one nudge asking the thread to continue and report its stage. If it is still stuck in the same stage `failAfterNudgeMinutes` later, the issue fails, Linear gets the reason, and the slot frees up. A thread T3 no longer has fails at once. Only Claude Code threads report activity as they work (usage snapshots), so a run on another harness (`jobs.provider`), Codex included, is never nudged or failed for being quiet; only a missing thread fails it.

## Sources

A source is where jobs come from and where the factory reports back. Linear is the only one shipped; the runner, the panel and ingest reach it only through its adapter, by the job's `source`, so a new source (GitHub Issues, Slack) is a new adapter and nothing else.

- **Identity.** A job row has `source` (text, a key of `SOURCES`), `external_id` (the source's own id), `id` = `<source>:<external_id>`, and `key`, which is unique across sources and is the branch name. A key is `<PREFIX>-<n>` or `<PREFIX>-<scope>-<n>`: PREFIX is uppercase letters and digits naming the source's namespace, scope an optional lowercase slug, n the source's number, at most 64 characters. Linear keys are the issue identifier (`FAC-123`). Build others with `jobKey(prefix, n, scope)` in `lib/factory.ts`: a GitHub issue would be `jobKey("GH", 42, "marshal-factory")` = `GH-marshal-factory-42`, a Slack thread `jobKey("SL", ts, channel)`. A claim skips a draft whose key is not one and reports it as an error once the rest are claimed.
- **Branches.** Attempt 1 runs on `factory/<key>`, attempt n on `factory/<key>-a<n>` (`attemptBranch`). A key ends in digits, so the suffix never reads as part of it, and `parseBranch` in `lib/factory.ts` is the one parser: the hooks, the report server's identity, ingest, cleanup, the inbox and the stage history all use it. `factory/FAC-59` and `factory/FAC-10-a2` parse as before. SQL that needs a job's branch uses `attemptBranchSql` in `lib/branch-sql.ts`.
- **Adapter.** `SourceAdapter` in `lib/sources/types.ts`: `ready` (drafts to claim, with key, title, URL, description, the write-back target and the source's state), `announceClaim`, `writeBack` (per stage), `replies` and `acknowledgeReplies` (answers to a waiting job), `stopWanted` and `confirmStop`, `note` (keyed comments: fallbacks, merge decisions and handovers), `labels` (for the review label), `overrides`, `reopen`, `describe` (the job's name in thread messages), and optionally `webhook`, `reply`, `file`, `uploadImage`, `localizeImages`, `syncLabelGroups` and `panelSyncLabelGroups`. Its row shapes (`writeback`, `source_state`) and display label live in `lib/sources/shapes.ts`; the deep link is the job's `url`.
- **Overrides.** `overrides(source_state)` returns `{ harness, runsOn, repository }`, each the names the ticket asks for (`lib/ticket-overrides.ts`); routing, launch planning and fallbacks read only that. Linear reads them from the Harness, Runs on and Repository label groups.
- **Write-back mapping.** Each adapter maps the factory's moments to its own states. Linear: claimed → In Progress with a "Picked up" comment (an attempt after a failure drops `factory-failed`), `pr` → In Review with the PR link and assumptions, `waiting` → the question as a comment, `failed` → Todo with `factory-failed` instead of `factory` and the reason, `merged` → Done, reopen after a stop → Todo. Stages it returns false for are marked synced with nothing written.
- **Adding a source.** Add its shapes to `SHIPPED` in `lib/sources/shapes.ts`, its adapter to `SOURCES` in `lib/sources/index.ts`, and, for push delivery, a `webhook` (the ingest Function serves `/webhooks/<source>` for every source that has one and passes its env, from which the adapter reads its scope). Keys come from `jobKey`. Claims, launches, stop checks and label sync loop over every source; the panel files new jobs through `panelSource()` (Linear), and so does [Slack](#filing-jobs-from-slack). `jobs.source` is text, so no migration is needed.
- **Boundary.** ESLint fails an import of an adapter module or the Linear client outside `lib/sources`, and a `sourceFor("<name>")` with a literal there; regressions in `scripts/` may drive adapters directly. `scripts/fake-source-regressions.ts` registers a fake source with `registerSource` and runs it through claim, launch, stage reports on its branch, PR, merge and write-back while every Linear call fails the test.

## Reporting

How a run's events reach ingest, and what survives an outage.

- **Outbox.** `hooks/report.ts` and the `factory-report` MCP server write every event to an outbox before posting it: one JSON file per event in `$FACTORY_STATE_DIR/outbox/`, by default `~/.local/state/marshal-factory/outbox/` (in a sandbox `/root/.local/state/marshal-factory/outbox/`, which hibernation snapshots keep). File names sort oldest first. A 2xx removes the file; a network error, a timeout, a cold start or any other status leaves it queued. A 400 is a body ingest will never take: a refused batch is retried one event at a time and only the events refused on their own move to `outbox-rejected/` next to it, to look at by hand. Past 1,000 queued events each append warns on stderr; past 10,000 the oldest are dropped, each one logged by kind and event id in `outbox-dropped.log`. The code is `lib/outbox.ts`.
- **Delivery and flush points.** Every hook and MCP call flushes the whole outbox, oldest first, in batches of up to 50, and stops at the first failure so nothing overtakes an earlier event. A hook spends at most 4 s on it and a `report_stage` call 3 s; what is left stays queued. The runner flushes this machine's outbox first thing on every tick, and a sandbox's through its Modal host before it hibernates, before it ends (teardown, a gone thread, an interrupted hibernate or wake) and right after it wakes, with the runner's own ingest URL and secret. A failed flush is logged (`outbox:flushed` with an error, `outbox:flush-failed`) and never holds back the step. Ingest stores each event id once, so a flush that overlaps another, or a redelivery after a lost answer, changes nothing. Hooks, MCP servers and the runner must share `HOME` or `FACTORY_STATE_DIR` for the runner to reach a local outbox.
- **Stages from Codex.** Codex has no hooks, so its `factory-report` server posts each `report_stage` call itself: the stage, summary, question, PR URL and merge assessment, the same event a Claude Code hook would send. It reports for the job named by `FACTORY_JOB_KEY` and `FACTORY_ATTEMPT` in its env, which a sandbox launch writes into Codex's `config.toml` together with `FACTORY_REPORTER=mcp` and `FACTORY_REPO`, or else for the factory branch checked out in its working directory. Its session id is `mcp:<attempt branch>`; the first call of each server also sends a `session_start` with id `mcp-start:<session>`, which opens the run and links it to the job, so the board shows the run's stages. It reads the ingest URL and secret from the same `config.json` as the hooks. A local Codex needs the server in its own `~/.codex/config.toml` with `FACTORY_REPORTER = "mcp"`; the installer does not write it.
- **Cost from Codex.** Codex writes each thread to `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<time>-<thread id>.jsonl` (in a sandbox `CODEX_HOME=/root/.codex`; on the runner Mac `$CODEX_HOME` or `~/.codex`). The first line is `session_meta` (thread id, root `session_id`, `cwd`, `git.branch`, and `source.subagent.thread_spawn.parent_thread_id` for a subagent), each turn writes a `turn_context` with its `model`, and each model call an `event_msg` `token_count` whose `info.total_token_usage` (`input_tokens`, `cached_input_tokens`, `cache_write_input_tokens`, `output_tokens`, `reasoning_output_tokens`, `total_tokens`) is the thread's running total. Cached input and cache writes are inside `input_tokens` and reasoning inside `output_tokens`, so the run's input is the uncached rest. On every tick usage reconcile reads, on the job's host in one `sh` command, the rollouts written to since the run opened, keeping only each file's `session_meta`, last `turn_context` and last total (`lib/codex-usage.ts`). A rollout is the run's when it is a root thread that started at most an hour before the run opened, in the run's worktree (the `cwd` its MCP server reported, or a directory inside it) or on its attempt branch; every thread of such a root's session (its subagents) is too. The newest root is the run's own usage and every other thread a subagent row `codex:<thread id>` with its own model, posted as the same `usage` event a Claude Code reporter sends, so ingest keeps the greatest totals and a replay never counts twice. T3's `thread show` names no Codex session id, so matching is by worktree and branch. The runner reads the rollouts once more before a sandbox hibernates or is torn down, since they go with it; a failed read is logged (`codex-usage:skipped`) and never holds up the teardown. A model switched mid-thread is priced at the thread's last model. A subagent whose last turn ended (`task_complete` after its last `task_started`) is settled with an `agent_stop`, and every subagent is once the job is merged or failed or its sandbox sleeps or ends, so none stays running. A usage read is never dated before the run opened, so it cannot move the run's start or widen the matching window. A rollout read before its first `turn_context` has no model: the runner keeps the model already recorded or posts nothing, and ingest never lets `unknown` replace a model, so a later read with the real model always lands.
- **No double reports from Claude Code.** Claude Code's hooks see the session id, so they stay the reporter there: its server entry (`.mcp.json`, `~/.claude.json`) carries `FACTORY_REPORTER=hook` and the server only validates. Wiring written before that variable falls back on `CLAUDECODE=1`, which Claude Code sets for every process it starts. A hook that fires twice for one call sends the same event id, which ingest stores once.
- **Inference stays the fallback.** For a harness that reports no usage the runner still reads GitHub and the thread (`runner/untracked.ts`). A stage the agent reported itself stands until the run has been quiet for `stoppedGraceMinutes`: only then does an open PR move the job to pr, or a settled thread to waiting. A late outbox delivery never undoes a newer stage, since ingest skips a stage event older than the job's.
- **Rollout.** [Rolling out a merge](#rolling-out-a-merge); the image bundles the hooks and the MCP server, so a change to them rebuilds it.

## Repositories

The `repo_settings` table is the registry of repos the factory works in, keyed by GitHub full name. Each row has a display name (null means the name part), `is_default`, `enabled`, a default harness (`provider`) and place (`execution`), both null for Settings, and the merge policy below. A partial unique index allows one default, and a check keeps it enabled. Migration 0027 registered every repo a job ran in and made the one with the newest job the default. Each runner registers its `factory.repos` checkouts at startup and makes its first one the default when none is; it never changes a row that exists.

- **Routing.** A claim routes each issue by its **Repository** label group child, matched case-insensitively by display name, then name part, then full name, and otherwise to the default repo. An unknown or disabled repo, or two Repository labels, go to the default too; the launch adds a note, posted on the issue once per attempt with the override fallbacks and recorded as `override_fallback` in the audit log. With an empty registry a job goes to the runner's first checkout. A retry is a new claim and routes again from the labels the issue has then. The capacity count covers queued jobs in the runner's checkouts and in every enabled repo.
- **Precedence.** A ticket's Harness and Runs on labels beat the repo's defaults, which beat Settings, field by field. A repo default harness other than the Settings one starts on its first current model; one no runner reports enabled is logged as `repo:default-skipped` and Settings apply.
- **Where it launches.** A local launch needs the runner's T3 and a checkout of the repo. Without a checkout, a job sent to local by Settings or its repo runs in a Modal sandbox when Modal can launch (logged as `repo:no-checkout`) and otherwise waits queued (`override:waiting`); a Local label falls back the same way and says so on the issue. A sandbox clones the repo from GitHub, so a repo with no checkout on any Mac can still run on Modal once the GitHub App can read it.
- **Labels.** `bun scripts/sync-linear-labels.ts` and the runner's optional daily sync create a Repository child per enabled repo by display name in `factory.teamKey`, along with the Harness and Runs on groups. They only add: a renamed repo gets a new child and the old one stays, still matched by name part or full name.
- **Panel.** `/repositories` lists the registry with open jobs, last job, where jobs can run (the best Modal readiness an online runner reports, and the machines whose inventory has a checkout) and the merging mode, and edits each repo through owner-only server actions (`app/actions/repositories.ts`, validated in `lib/repositories.ts`). The default can't be disabled, a disabled repo can't become the default, and display names stay unique. **Add repository** onboards a repo the GitHub App reaches; see [Onboarding a repository](#onboarding-a-repository). **New job** has a Repository select and always files the issue with its Repository label; a follow-up from the inbox goes to its job's repo while it is enabled.
- **Filter.** The Jobs page and the Inbox filter by `?repo=owner/name`, which is remembered in the `jobs_repo` cookie; an explicit param wins and `?repo=all` shows every repo. The filter applies in the browser to the loaded feeds. The rail's inbox count stays global.

## Onboarding a repository

Adding a repo from the panel registers it and onboards it: the factory gets a setup recipe for it, the secrets the recipe names, and a warm per-repo Modal image built from it, so its jobs start with everything installed. The state is on the registry row (`onboarding_state`, `onboarding_detail`, migration 0028); a repo registered before onboarding has none and launches from the base image as before. The runner code is `runner/onboarding.ts`, the model `lib/onboarding.ts`, the recipe `lib/recipe.ts`.

- **The recipe.** `.factory/setup.json` in the repo: `system` (apt packages), `runtimes` (`node`, `bun`, `python` pins, installed only when the sandbox lacks that version), `setup` (commands run from the repo root), `checks` (`test`, `lint`, `typecheck`, `build`), `env` (names, purposes and whether a check needs them; never values) and `warmKey` (globs whose change makes the image stale; default every common lockfile, and the recipe itself always counts). Services such as databases are not supported yet; a recipe that lists `services` is refused with that reason.
- **Adding.** **Add repository** asks GitHub, with the App's JWT, for every repo its installations reach and leaves out registered and archived ones. Picking one (owner only) inserts the row, enabled and not the default, in `analyzing`, with an `onboard_repo` intent in the same transaction, then adds its **Repository** label child in `FACTORY_TEAM_KEY`. A label that cannot be added is shown, and the repo is added anyway. The panel needs `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` and `LINEAR_API_KEY`, as it does for merging and new jobs.
- **States.** `analyzing` → `needs_input` when a required env var has no value → `building` → `ready`; `rebuilding` while a newer image builds (the old one keeps serving); `failed` with the reason and a redacted log excerpt, while an image built before still serves. Retry onboarding starts over from `analyzing`.
- **Onboarding run.** Any runner takes `onboard_repo`. When main has a valid recipe, no agent runs: the recipe goes to the build, which also runs its checks. Otherwise the runner starts a sandbox from the base image (tagged `purpose=onboarding`, never reaped as a job's), leases a free Codex slot whatever the harness (unlike a job, where only Codex needs one), sets it up like a job's but without the hooks' ingest config, and starts one thread on the Settings harness on branch `factory/onboarding` with `playbooks/onboarding.md` in its first message. The agent writes the recipe, runs setup and every check until they pass or says why one fails, names the env vars it needs, commits the recipe alone, pushes, opens **Add the factory setup recipe**, and writes `/work/onboarding/result.json`. Each tick reads the thread; once it settles the runner reads the result, hands the login back, ends the sandbox, and records the recipe, PR, checks and summary. An agent still running after 90 minutes is stopped and the repo fails.
- **Secrets.** A repo's values live in the Modal secret `mf-repo-<owner>-<name>` (lowercased, other characters as `-`). The panel's detail pane lists each env name with its purpose. When the Vercel project has `MODAL_TOKEN_ID` and `MODAL_TOKEN_SECRET`, checked per request, the form sends the values to an owner-only server action that upserts them into the secret with the Modal SDK and records only the names; without them it shows the CLI command instead. `bun scripts/repo-secret.ts owner/name NAME` on the runner Mac reads the value from stdin (hidden on a terminal, or piped), upserts it with `~/.modal.toml`, and records the name. A value never reaches the database, an intent, an event, a log or an error message. With every required name set, the repo moves on to `building`. Build sandboxes and job sandboxes for the repo, woken ones included, get the secret attached by name.
- **Warm image.** One build at a time per machine. A sandbox from the base image gets a GitHub token, clones origin/main to `/work/repo` and runs a script in the background: system packages, missing runtimes, each setup command (stopping at the first failure; the exit code names the step), and for a committed recipe new to the factory, each check with its exit code. When it exits 0 the runner records the commit and a hash of the files the warmKey matches, removes the token and the build files, snapshots the filesystem (kept indefinitely), records the image with the base image's versions and build time and the recipe hash, ends the sandbox and deletes the previous image. A build still running after 45 minutes is stopped.
- **Launches.** A repo's Modal job starts from its warm image while that image's base matches the current base image (same pinned versions and build time); the clone is skipped: `/work/repo` moves to `origin/main` and the setup commands run again, up to 3 minutes, a failure only logged. The thread is told to run the recipe's setup in its own worktree. Otherwise the job starts from the base image as before, and the runner logs `sandbox:warm-image-outdated`. A repo still onboarding without any warm image cannot run on Modal: routing treats it like Modal not being ready, so the job runs locally if it can or waits. Repositories shows the same per repo.
- **Freshness.** Each GitHub push to a default branch also records a `repo_push` intent with the changed paths. For an onboarded repo, a push that changes `.factory/setup.json` takes main's recipe (this is how a merged recipe PR lands) and rebuilds; one that touches the warmKey rebuilds; anything else is ignored. A push during a build queues one more build after it. When the base image is rebuilt or re-pinned, ready repos rebuild lazily, one per machine at a time, and their jobs use the base image until then. **Rebuild image** asks for one by hand.
- **By hand.** `bun scripts/repo-image.ts owner/name --recipe /path/setup.json --check "bun test" --delete` builds a warm image as the runner does without touching the registry, checks it from a second sandbox, and deletes it.

## Per-ticket overrides

Two Linear label groups let one issue pick its lead harness and where it runs, over Settings and the repo's defaults, field by field. Linear allows one child per group on an issue. A third, **Repository**, picks the repo ([Repositories](#repositories)).

- **Harness**: one child per enabled harness the machines report, by its display name (Claude Code, Codex, Cursor). A ticket on another harness than Settings runs on that harness's first current model from T3's manifest; the Settings model applies only to the Settings harness. There is no per-ticket model, since the lead agent fans out to other models itself.
- **Runs on**: Local or Modal.
- **Creating the groups.** Run `bun scripts/sync-linear-labels.ts` on a machine with the runner's config and `.env.local`. It creates the missing groups and children in `factory.teamKey` only, prints what it created, and renames, moves or deletes nothing; a name already taken outside its group is reported for you to fix in Linear. Run it again after enabling a harness. With `factory.syncLinearLabels: true` the runner does the same at startup and about once a day. The panel's **New job** has **Harness** and **Runs on** selects (default: Settings) and files the issue with those labels, creating any that are missing.
- **Reading.** A claim stores each label with its group in `source_state.labelGroups`, and the Linear adapter turns those into the normalized overrides the runner reads ([Sources](#sources)); rows claimed before this have none and so no overrides. A retry is a new claim and reads the labels again, so changing a label before retrying switches the harness or place.
- **Fallbacks.** A Harness label that names no reported harness, a disabled one, one with no current model, or two Harness labels run on the Settings harness. A Modal ticket on a runner where Modal cannot launch (no image or an outdated one, no Modal token, or no usable Codex slot for a job that runs on Codex there) runs locally if the runner's T3 is up, and otherwise stays queued; one whose slots are only busy stays queued without falling back. A Local ticket on a runner without a running T3 runs on Modal if it can launch there, and otherwise stays queued. In a sandbox a harness it lacks runs on Codex, as for Settings. Each fallback is posted on the issue once per attempt, under a comment id derived from the attempt, and recorded in the job's audit log. Settings alone never fall back: with Modal in Settings and no image, jobs wait as before.
- **Recorded.** Each launch records `jobs.provider`, `jobs.model`, `jobs.execution` and `jobs.ticket_overrides` (what the ticket applied and each fallback note). Cards show where a job runs (**Modal sandbox** with its running or hibernated badge, or **Local · machine**) and the harness; the model is in run detail, which also shows the runner as **Managed by** for a sandbox job and what came from the ticket.

## Running jobs in Modal sandboxes

With **Run jobs on** set to Modal in Settings, the runner starts each new job in its own [Modal](https://modal.com) sandbox instead of its own T3. The runner Mac still claims, watches and writes back; only the thread, its worktree and its tools move into the sandbox. Jobs already running keep the place they started in.

- **Prerequisites, all on the runner Mac.** Settings lists each one, with what is missing.
  - The Modal CLI and a token: `uv tool install modal`, then `modal token new`. The token goes to `~/.modal.toml`, which the runner reads through `HOME`.
  - The sandbox image: `bun scripts/sandbox-image.ts`. It builds an image with T3, Claude Code, Codex and PStack at the versions `factory.sandbox` pins (see **The sandbox image** below), `gh`, and the factory's bundled hooks and MCP server, and records its id, versions, build time and factory commit in `~/.config/marshal-factory/sandbox-image.json`.
  - A Claude token, optional: run `claude setup-token` and add the token as `CLAUDE_CODE_OAUTH_TOKEN=...` to `.env.local` in the runner's checkout, then restart the runner (`bun scripts/install-runner.ts --uninstall && bun scripts/install-runner.ts`). The runner loads `.env.local` at startup; the LaunchAgent itself only sets `PATH`, `HOME` and `T3CODE_CLI_PATH`, so the token never lands in the plist. Each sandbox gets it as an environment variable through a Modal secret. Without it, Claude Code jobs run on Codex (`factory.sandbox.codexModel`).
  - Codex login slots: one `CODEX_HOME` folder per ChatGPT login, each held by one sandbox running Codex at a time. A Claude Code job holds none, so with a Claude token the cloud is ready without any slot; Codex jobs then wait queued (`sandbox:no-slot`) until one is free. `mkdir -p ~/.codex-factory-1 && CODEX_HOME=~/.codex-factory-1 codex login --device-auth` makes the default slot. For more, log in to `~/.codex-factory-2` and so on, and list every folder in `factory.sandbox.codexSlots`. A slot whose login Codex refuses in a sandbox is marked unusable and skipped until you log in to it again; the job's audit log records it.
  - Room: `factory.sandbox.maxParallel` (4) caps the sandboxes running at once on a runner, in any stage and slot or not: every job whose sandbox Modal still runs, every launch still setting one up, and every wake under way. A hibernated job holds no room, and every job still counts against `factory.maxInFlight` (4), so raise both to run more jobs side by side.
- **The sandbox image.** `factory.sandbox` pins every tool a job runs with:

  | Key | Default | Installed with |
  | --- | --- | --- |
  | `t3Version` | `0.1.3-nightly.20261023.3566` | T3's install script |
  | `claudeCodeVersion` | `2.1.310` | `npm i -g @anthropic-ai/claude-code@<version>` |
  | `codexVersion` | `0.164.0` | `npm i -g @openai/codex@<version>` |
  | `playwrightMcpVersion` | `0.0.83` | `npm i -g @playwright/mcp@<version>`, then Chromium and its OS libraries from the playwright CLI that package bundles |
  | `pstack.repo`, `pstack.commit`, `pstack.version` | `michael-denyer/pstack-claude` at `614d2f9791dd…`, `0.9.69` | the repo fetched at that commit into `/opt/pstack` |

  Neither CLI can pin a marketplace to a commit, so the build adds the `/opt/pstack` checkout as a local marketplace to both and installs `pstack@pstack-claude` at user level: `claude plugin marketplace add /opt/pstack && claude plugin install pstack@pstack-claude`, and the same with `codex plugin marketplace add` and `codex plugin add`. Claude Code inside T3 loads it because the sandbox's `claudeAgent` instance has no home path, so T3 keeps user settings in its setting sources. Codex gets it from the image's `/root/.codex/config.toml`, which a launch extends with the report server instead of replacing; PStack's Codex session hook still waits for trust through `/hooks`, its skills do not. The build then checks inside the sandbox that `t3 --version`, `claude --version` and `codex --version` print the pins, that both `claude plugin list` and `codex plugin list` show PStack enabled at the pinned version from the pinned commit, and that its skills are on disk; any mismatch fails the build and records nothing.
  - **Playbooks.** The build copies `playbooks/factory.md` and `playbooks/onboarding.md` to `/opt/marshal-factory/playbooks/`, reads them back and records a hash of their content as the `playbooks` version. The runner pins the hash of its own checkout's playbooks, so editing either file makes the image outdated (`Rebuild the sandbox image: Factory playbooks <old> → <new>`) until it is rebuilt.
  - **Readiness.** An image whose recorded versions differ from any pin, or that lacks one (built before the pin existed), is outdated. The runner launches nothing from it, exactly as with no image: jobs stay queued and the runner logs `sandbox:no-image` with, for example, `Rebuild the sandbox image: Claude Code 2.1.309 → 2.1.310`. Settings and Repositories show the same line. Each launch also runs `claude plugin list --json` in the new sandbox and logs `sandbox:no-pstack` when PStack is not enabled; the job still runs.
  - **Bumping a pin.** Set the new value under `factory.sandbox` in `~/.config/marshal-factory/config.json` (for PStack, the marketplace commit and the plugin version its `.claude-plugin/marketplace.json` declares at that commit), or change the default in `lib/config.ts`, restart the runner, then rebuild. Until the rebuild, Modal launches wait.
- **Launch.** A launch whose thread runs on Codex leases a free slot first; a Claude Code launch leases none. It creates the sandbox from the image and records its id on the job before anything runs in it, then installs the slot's Codex login (when it holds one), a GitHub installation token, the hooks' config, clones the repo, wires it and starts `t3 serve`. A Claude Code job whose token the sandbox's claude refuses falls back to Codex and leases a slot then; with none free the sandbox ends and the job retries next pass. The thread starts from there like a local one. The sandbox's GitHub token is rewritten every 40 minutes.
- **Hibernation.** A job waiting in pr or waiting whose thread has settled for `factory.sandbox.hibernateAfterMinutes` (5) gives its sandbox up: the refreshed Codex login goes back to its slot (if it holds one), T3 stops, the filesystem (worktree, T3's state, Codex sessions) is snapshotted, the sandbox ends and the slot is freed. The card shows **Modal sandbox** with a **hibernated** badge.
- **Wake.** An operation that must reach the thread, such as an answer or a conflict send-back, starts a new sandbox from the snapshot with a free slot (only for a Codex thread), a fresh token and a new `t3 serve`, then deletes the snapshot. At `maxParallel` the wake waits: the answer, conflict send-back or verification that wanted it stays queued and tries again on a later tick. A snapshot lives `factory.sandbox.snapshotTtlDays` (30); after that the thread counts as gone.
- **Teardown.** A merged or failed job's login goes back to its slot, and its sandbox, snapshot and slot are released. Every 5 minutes the runner also ends sandboxes of its label that no job points at, and frees slots no running sandbox holds, so a crash leaks nothing for long.
- **Open in T3.** For a running sandbox, run detail's **Open in T3** asks the job's runner (an `open_t3` intent, owner only) to mint a pairing token inside the sandbox with `t3 auth pairing create --ttl 15m`. The panel shows the link once; paste it into T3 → Add environment. T3's port is exposed as an encrypted Modal tunnel and refuses any client that has not paired, so the port is useless without a token. The link is stored only in the intent's result until the panel shows it, is cleared there on reading or after 15 minutes, and appears in no log or live feed. A hibernated job is not woken for it; it wakes on its own when the job needs it. Sandboxes started before this existed get the tunnel the next time they wake.
- **Costs.** A sandbox bills by the second while it runs, idle or not, for what it reserves: `factory.sandbox.cpu` (1 core) and `memoryMiB` (2048), bursting to `cpuLimit` (2) and `memoryLimitMiB` (8192). Hibernation is what keeps a job waiting on review cheap; a hibernated job keeps only its snapshot. The Claude token and ChatGPT logins bill to their subscriptions, never per token.
- **Limits.** A sandbox lives at most `factory.sandbox.timeoutMs` (4 hours); one that hits it is gone, and its job follows the gone-thread rules. Claude Code reports agents and cost through its hooks. Codex reports its stages through the factory-report MCP server and its cost through its session logs ([Reporting](#reporting)); the quiet-run watchdog does not apply to it. Its card says **Codex · cost unknown** until the runner has read a usage on a priced model. Images attached to an issue stay on the runner Mac; the thread gets their links.
- **Rebuilding the image.** The runner rebuilds the image itself when a pin or a playbook in its checkout differs from the recorded image (`runner/base-image.ts`): its tick starts the build and moves on, one build at a time per machine (`sandbox-image.json.lock` keeps a build by hand out too), and queued Modal jobs launch once the new image lands. The log shows `sandbox-image:started`, `:build`, `:landed` and `:failed`, and Settings shows the rebuild under way or why it failed. A failed build keeps the old image recorded and is retried after an hour, or at once when a pin changes again. A first build, with no image recorded, stays manual. The runner does not notice a change to `hooks/`, `mcp/factory-report.ts` or what they import (`lib/outbox.ts`, `lib/report-identity.ts`, `lib/evidence.ts`, `lib/recipe.ts`), which the image bundles, `hooks/verify.ts` (`factory-verify` on `PATH`) among them; [Rolling out a merge](#rolling-out-a-merge) rebuilds for those, or run `bun scripts/sandbox-image.ts` by hand. A sandbox from an older image keeps reporting the old way: its hooks post once without an outbox, and its Codex report server only validates. `MARSHAL_FACTORY_SANDBOX_IMAGE` writes the record elsewhere, for a trial build that live runners should not pick up. New launches use the new image; a hibernated job wakes from its own snapshot.

## Merge decisions

Every run ends in one of three ways: the factory merges it, it hands the PR over for your review, or the agent asked before building (`waiting`).

- **One merge path, three entry points.** Every merge the factory makes goes through `mergeNow` in `runner/merge-service.ts`, on the job's own machine. It is reached three ways: **auto** (the timer's decision under Merge when confident, `decideMerges` in `runner/merge-decision.ts`), **inbox** (**Approve and merge**) and **run detail** (**Merge** on a job in pr). The last two record the same owner-only `approve_merge` intent and differ only in `via`. Each merge gets the same treatment: the head re-read and pinned, the repo's merge method, the App's push access, a `merging` note stored before GitHub is asked so a crash right after is still recorded, the merge recorded once on `merge_decision.merged` with its `via`, the stage event to merged, the post-merge watch, the decision comment on the PR, the note on the Linear issue, and the audit rows. `merge_succeeded` is by `factory` for auto and by you for an approval, and its detail says `via auto`, `via inbox` or `via run_detail`. The factory's revert of a red merge merges in the same file. The panel never calls GitHub's merge endpoint: lint (`no-restricted-properties` on `mergePull`) refuses it anywhere but `runner/merge-service.ts`.

- **Autonomy, per repo.** **Repositories** sets it for each registered repo. **Off** (the default) evaluates nothing: a PR is just ready for your review. **Trial** evaluates every PR and shows **Would merge (trial)** or the reasons it hands over, but never merges. **Merge when confident** (`auto`) merges every PR the decision clears. **Require Bugbot review** is edited there too and lives in the `repo_settings` row (`require_bugbot`). The older `protected_paths` and `max_changed_lines` columns are no longer read or written. To switch a repo to auto, run it on trial for a while, read the decisions it would have made, then pick **Merge when confident** on its Repositories entry; the next tick re-decides its open PRs.
- **The agent's assessment.** With stage `pr` the agent reports its interpretation, every assumption, a recommendation, its confidence (`confident`, and a `reason` when it isn't) and optional `notes`. It recommends `merge` whenever it is confident it built what the issue asked for and that it works, additive changes the issue asked for included, and `handover` only when it isn't; the schema refuses a merge without confidence, a handover with it, and a missing reason. The decision then gives one agent reason, "The agent isn't confident: <reason>", or "The agent didn't report an assessment." when there is none. Reports in the older six-check shape (`checks`, `reviewFocus`), from agents started before the change, are still accepted: a merge reads as confident, a handover as not confident with its failed checks' notes (or else its review focus) as the reason, and the review focus becomes the notes. Ingest stores the latest one on `jobs.merge_assessment` in the current shape; rows stored before keep the six checks and are mapped when read (`parseAssessment` in `lib/assessment.ts`). The stage event keeps each report as sent, for history. Codex reports one through the factory-report MCP server too, and its PRs go through the same limits as Claude's.
- **Cost.** A run's cost is measured, never a reason to hand over. It is known once some usage was recorded for the attempt branch and every run and subagent with tokens is on a model with a price. Prices are USD per million tokens in `lib/pricing.ts`: Claude from Anthropic's pricing page, OpenAI's `gpt-6-astra`, `gpt-6.1-sol`, `gpt-6.1-terra`, `gpt-6-luna`, `gpt-6-sol` and `gpt-5.6-*` from [OpenAI's pricing page](https://platform.openai.com/docs/pricing) (Standard tier, short context, read 2026-10-27), with cached input and cache writes priced on their own. A key prices its model id and dated snapshots of it (`gpt-6-astra-2026-09-01`), never a longer name (`gpt-6-sol-mini`). Codex under a ChatGPT login is not billed per token; its cost is what the same tokens cost on the API, and a request over 272K input tokens costs more than counted. `factory.pricing` in the runner's config overrides a model's price (`{ "gpt-6.1-sol": { "input": 2, "output": 10, "cacheRead": 0.1, "cacheWrite": 2.5 } }`) or makes it unknown (`null`); the runner's spend reconcile uses it, the panel shows the defaults.
- **Hard limits.** These are facts, not the agent's judgement. The runner hands over regardless of the agent when: a check failed on the head, the PR conflicts with its base, Bugbot has an unresolved medium or high finding (with **Require Bugbot review**), or the issue has the `review` label. Size, retries, protected paths, dependency major versions and a branch behind its base are the agent's to weigh in its confidence; when branch protection requires an up-to-date branch, GitHub refuses the merge and the decision hands over with its reason. Under trial and auto it also hands over unless the head is verified at that exact commit (see Evidence): no checks defined for the repo, a check that failed at the head, or no valid evidence for the head that the runner can't settle by running the checks itself. While checks, Bugbot or GitHub's mergeability check are still running the decision is pending, for up to 60 minutes after the head was first seen; then it hands over.
- **Repos without CI.** A head with no check run (Bugbot's aside) and no commit status counts as pending while CI may still start. Once it is older than `noCiGraceMinutes` (5), counted from the later of its commit time and when the factory first saw it, and its base branch requires no status check, its checks are `none`: the repo has no CI. Required checks come from the base branch's protection (`GET /repos/{repo}/branches/{base}`) and the rulesets that apply to it (`GET /repos/{repo}/rules/branches/{base}`); one the App can't read (403, 404) counts as requiring none, and a required check that never reported keeps the head pending, then hands over at the timeout. `none` is no failure. Under trial and auto the factory's own evidence at the head is then the only CI, required as for any repo (see Evidence), and a merge says "No CI on this repo; relying on the factory's own checks at <sha>." The owner's approval is not blocked by it.
- **Require Bugbot review.** On by default, and on for every repo registered before the setting existed (migration 0033). When on, a decision waits for Bugbot's review and hands over on its unresolved medium or high findings as above. When off, the decision ignores Bugbot entirely: no waiting, no timeout, no findings. Onboarding sets it from the recipe PR: on as soon as a Bugbot check run shows up there, off when none has within `noCiGraceMinutes` after the PR was recorded (`onboarding_detail.bugbotProbe` holds the PR until then). A repo onboarded from a recipe already on main has no recipe PR and keeps it on; turn it off on its Repositories entry if the repo has no Bugbot.
- **Cadence.** Each timer tick reads the head of every PR the machine holds in pr. A settled decision is recomputed when the head, the pr report, the autonomy or the head's evidence changes, or after 15 minutes; a pending one every tick. It wakes a hibernated sandbox only to verify a head under auto (see Evidence). The decision lands on `jobs.merge_decision`, and the job's audit log gets a row whenever it changes. The card shows one line under its title, and run detail a Merge decision section with every reason and the agent's assessment.
- **Auto-merge.** A merge decision under auto is never taken from storage: it merges only in the pass that read the PR, its checks, Bugbot and the labels, and it reads the head again right before the merge. The merge is `PUT /repos/{owner}/{repo}/pulls/{n}/merge` as the GitHub App with `sha` set to the evaluated head, so a push in between makes GitHub refuse it. It squashes when the repo allows squash merges, else uses the first method it allows (merge commit, then rebase). The commit title is `<PR title> (#n)` and the body the run's summary plus "Merged by the factory". A merge GitHub reports as already done at that head counts as the factory's. The job then moves to merged the usual way (Linear to Done, sandbox teardown), and the audit log gets `merge_succeeded` by `factory`, `via auto`, with the reasons and the assessment.
- **When GitHub refuses.** A 403 or 404 (the App lacks the permission), a 405 (branch protection, required reviews) or a 409 at an unchanged head hands the PR over with "The factory's GitHub App can't merge in this repo: …" and one audit row. That head is never tried again; a new push is decided afresh. The App needs **Contents: read and write**, **Pull requests: read and write**, **Checks: read** and **Commit statuses: read** (the manifest in `scripts/setup-github-app.ts` asks for these; an App created before statuses were added needs **Commit statuses: read** added in its GitHub settings, then the installation's new permissions accepted). Before merging, the runner reads the repo and hands over at once when the token has no push access.
- **Decision comments.** The PR gets one comment marked `<!-- marshal-factory:decision -->`, edited in place whenever the decision's text changes: **✅ Merged by the factory** with the interpretation, the assumptions, the agent's confidence and its notes; **Ready for your review** with the reasons and the notes; or, on trial, **Would merge (trial)** or **Would hand over (trial) because …**. The Linear issue gets a short comment for each merge, handover, revert or failed revert, never for a pending tick. Fingerprints of the last texts posted live on `merge_decision.comments`, and Linear comment ids derive from them, so a replay posts nothing twice.
- **Watching main after a merge.** For `factory.postMergeWatchMinutes` (60) after its own merge, the runner reads the merge commit's check runs and commit statuses on the base branch, Bugbot's aside. Green ends the watch; checks still running at the end of the window end it without a verdict. Red reverts it: in a temporary worktree of this machine's checkout of the repo, it fetches the base, branches `factory/revert-<n>` from `origin/<base>`, runs `git revert --no-edit` (`-m 1` for a merge commit, the whole range for a rebase merge), pushes with an installation token and opens `Revert "<title>" (#n)` listing the failed checks, then merges it at once. git reads the token from an environment variable through a one-off credential helper, so it never appears in a URL, the arguments or a log line. The worktree and the local branch are removed afterwards. The watch state (`watching`, `green`, `expired`, `reverted`, `revert_failed`) lives on `merge_decision.watch`, with an audit row when it ends. A revert posts "Reverted: main went red after merge — <checks>" on the Linear issue; the issue stays Done, so reopen it if the work should be retried. A revert that fails (a conflict, a push or merge GitHub refuses) stops there: the card says **Revert failed after main went red**, Linear gets the reason, and the revert is never retried. Revert it by hand.

## Evidence

A stage says what the agent reported. Evidence says what ran, what passed and at which commit. The merge decision reads the evidence; the stage moves freely as before.

- **The record.** An `evidence` event (`lib/evidence.ts`) names the job, the attempt, the repo, the full commit sha, whether the tree was clean, who produced it (`agent` or `runner`), where the checks came from (`recipe`, `package` or `none`) and each check: `test`, `lint`, `typecheck`, `build` or `custom` (the runner's setup step), its command, exit code, start, duration and the last 40 lines of output (at most 4000 characters), and whether it passed. Ingest keeps one row per job and commit in `job_evidence` (migration 0031); a later run at the same commit replaces it, an out-of-order older one doesn't, and a dirty run never replaces a clean one. The job's newest evidence for its current attempt, without output, is on `jobs.evidence` for cards and the inbox. Evidence opens no run.
- **Redaction.** Before a tail is kept, values assigned to the recipe's env names and to known secret names (`GITHUB_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, `DATABASE_URL`, …), bearer and basic tokens, URL userinfo, GitHub, OpenAI and Slack token shapes and any 40+ character token-like string are replaced with `[redacted]`. `factory-verify` also replaces the literal values of those env vars and of the ingest secret wherever they appear.
- **factory-verify.** `bun <factory root>/hooks/verify.ts` (in a sandbox `factory-verify` on `PATH`) runs in the agent's worktree: the recipe's checks from `.factory/setup.json`, else the `test`, `lint`, `typecheck` and `build` scripts of `package.json` with the package manager the lockfile names. It records `git rev-parse HEAD` and `git status --porcelain`; uncommitted changes, or a HEAD that moves while the checks run, mark the evidence dirty, so it proves nothing about the commit. Every check runs even after one fails. It posts through the outbox like the hooks, so an ingest outage only delays it, and exits 0 only for a clean tree with every check passed (1 otherwise, 2 outside a git repo). `--json` prints the event, `--no-post` keeps it local, `--timeout-minutes N` changes the 20-minute limit per check. The playbook runs it on the final pushed commit before stage `pr`, and the `report_stage` reply for `verifying` and `pr` names the command.
- **Verified at head.** Under trial and auto the decision needs evidence for exactly the PR head, from a clean tree, with every check passed. Required checks are the ones in the recipe onboarding recorded for the repo, each with its recorded command; a repo with no recorded recipe requires the checks its evidence found. A repo with no checks hands over with "No checks defined for this repo." Failed checks hand over with "Checks failed at <sha>: test, build." Missing, stale (an older commit), dirty, incomplete or untrusted evidence waits when the runner can verify the head itself, and otherwise hands over with "Not verified at <sha>: …" and why the runner couldn't. CI, Bugbot and mergeability stay hard limits alongside it, and the 60-minute wait covers the verification too. The owner's approval still overrules the decision; the inbox shows the evidence so the owner can see what was proven.
- **Trusted commands.** An agent plans its checks from its own worktree, so a PR could rewrite `.factory/setup.json` or a `package.json` script to `true` and pass them. Evidence whose `test`, `lint`, `typecheck` or `build` command differs from the one in the recorded recipe is `untrusted`, never `verified`: the runner settles it by running the recorded commands itself (a Modal job under auto), and otherwise the decision hands over with "the checks ran other commands than the recipe records for test". The setup step isn't compared. Independently of the evidence, a PR hands over when it edits what the trusted commands depend on, even with verified evidence and without a runner run: `.factory/setup.json` ("edits the recipe the factory trusts"), `.github/workflows/**` ("edits CI workflows"), or `package.json` when a script a check runs, or one that script calls, differs between the base branch and the head ("edits the check scripts the factory trusts: package.json scripts.test"). The runner reads both `package.json` versions through the GitHub App, only for a PR that touches it, so a dependency-only change doesn't hand over; if either can't be read it hands over. A repo with no recorded recipe has no commands to compare, so only the file rules protect it. Not covered: files a script runs, such as lint or test configs, and `package.json` files below the root. The owner's approval overrules all of it.
- **The runner's own run.** Under auto, for a job that has a Modal sandbox (running or hibernated), when verification at the head is the only thing between the PR and a merge, the runner checks out that exact commit in a fresh worktree of `/work/repo` in the sandbox (`/work/verify/<sha>`), runs the recorded recipe's setup and checks (else the commit's own recipe, else `package.json` scripts) and posts the result as `runner` evidence. It wakes a hibernated sandbox for it and keeps it from hibernating while the checks run. It runs at most once per head and two at a time per runner, in the background; the decision says "Waiting for verification at <sha>." until the evidence lands. A run that can't happen (the commit isn't on the branch, the sandbox is gone, ingest refused it) is recorded on `merge_decision.verification` and hands that head over; a new push starts afresh. Local jobs and trial never get a runner run, so they rely on the agent's `factory-verify`.
- **Panel.** Cards and the job list show **Verified at <sha> · 4/4 checks**, **Checks failed at <sha> · 3/4 checks**, **Not verified at <sha> · uncommitted changes** or **Not verified at head** next to the reported stage. Run detail has an Evidence section with each commit's checks, who ran them, durations, exit codes and the output tail (open for a failed check). The inbox handover detail shows the latest evidence, and the PR comment for a merge names the commit and the checks it rests on.
- **Rollout.** [Rolling out a merge](#rolling-out-a-merge). An ingest that predates `evidence` events answers 400 and the outbox sets them aside in `outbox-rejected`, so run `factory-verify` again after it redeployed; a sandbox from an older image has no `factory-verify`, so only the runner's own run can verify its head. Repos on trial or auto hand over every PR without evidence for its head, so run `bun scripts/install-target.ts <repo>` again in each wired repo for the playbook before switching one to auto.

## Screenshots

The playbook has the agent look at every page it changes. Screenshots record that it did, and show the owner what it saw.

- **Attaching.** In a sandbox the `playwright` MCP server writes screenshots to `/work/browser` (`SCREENSHOT_DIR` in `lib/screenshots.ts`). The `pr` assessment may name up to six of them in `screenshots`, each a `file` (relative to that dir, or absolute inside it) and a `caption`. `report_stage` refuses the report when a file is missing, outside the dir (symlinks included), over 1 MB, or not a PNG, JPEG or WebP image, so the agent fixes it and reports again.
- **The record.** The reporter (the PostToolUse hook under Claude Code, the MCP tool under any other harness) sends one `screenshot` event per file ahead of the stage event, with the image as base64 and an id from the stage event and the file, so a retried report stores each image once. Ingest keeps the bytes in `job_screenshots` (migration 0037), keyed by the stage event and the file, and stores the event in `events` without them. The outbox caps a batch at 4 MB of JSON, so a few images never make one request too large.
- **Panel.** The inbox item and the Merge decision section of run detail show the current assessment's screenshots with their captions; each opens full size. `/api/jobs/<key>/screenshots/<n>?v=<pr report id>` serves them. `jobs.assessment_event_id` (migration 0038) names the pr report the assessment came from, so the images stay after later stages move the job on, and the route sits behind the owner-only proxy like every panel route. A URL for an earlier report, or an image that hasn't arrived, answers 404.
- **Merge decision.** Under trial and auto, a job that ran in a Modal sandbox hands over when its PR changes UI files (`.tsx`, `.jsx`, `.vue`, `.svelte`, `.astro`, `.html`, `.css`, `.scss`, `.sass`, `.less`; `UI_GLOBS`) and the assessment attached no screenshots: "The pull request changes UI files (…), but the agent attached no screenshots." Local jobs have no browser, so they are not held to it. The owner's approval overrules it.
- **Rollout.** [Rolling out a merge](#rolling-out-a-merge). An ingest that predates `screenshot` events answers 400 and the outbox sets them aside. A sandbox from an older image reports no screenshots, so its UI PRs hand over until it is relaunched.

## Needs you inbox

`/inbox` lists every job waiting on you, so you can act without leaving the panel; GitHub stays the place for full diffs. The rail's **Inbox** entry and the **Jobs** header show the live count. The rules are in `lib/inbox.ts`:

- **What lands there.** Questions (stage `waiting`), failed reverts (a factory merge whose watch ended `revert_failed`) and stops the runner could not confirm ([Stopping a job](#stopping-a-job)) first, then pull requests ready for your review (stage `pr` with a handover decision, autonomy off, no decision yet, or trial's **Would merge**), then failures (stage `failed`) you have not dismissed. Newest first within each. A pending decision or a merge in flight is still the factory's and stays out.
- **What an item shows.** Why it is there (the decision's reasons, the question, the failure or the failed revert), the agent's confidence and why, its notes and assumptions, Bugbot's unresolved findings by severity, and the changed files with their line counts, each linking to the PR's files on GitHub. The runner stores the files and findings it read on `merge_decision.review`; for autonomy off, which reads nothing, the panel's server reads them through the GitHub App (`/api/jobs/<key>/review`). The browser never calls GitHub.
- **Actions.** Each is owner-only, checks that the job still offers it, and records an intent for the job's runner keyed by a request id, so a double submit records one. The detail pane follows the intent until the runner handles it, then shows a toast or the runner's refusal inline.
  - **Approve and merge** (`approve_merge`) merges through the factory's one merge path (`runner/merge-service.ts`, see Merge decisions), pinned to the head you reviewed. Only facts stop it: a red or running check, a conflict or unknown mergeability; a merge GitHub refuses, for example for a branch protection requires up to date, hands over with GitHub's reason. A repo without CI (checks `none`, see Merge decisions) has nothing running, so it doesn't stop an approval. The agent's reasons and Bugbot's findings are yours to overrule. The audit log gets `merge_requested` and then `merge_succeeded` by you, or `merge_failed` by you with the reason it stopped. Run detail's **Merge** records the same intent, with `via: run_detail`, for any job in pr the factory is not already merging: its dialog shows the head it read through the App when run detail opened (`/api/jobs/<key>/merge-target`), pins the approval to it, then follows the intent like the inbox does, a toast when it merged and the refusal inline.
  - **Request changes** (`request_changes`) wakes a hibernated sandbox, sends the thread "The reviewer requested changes on <PR>: … Update the same branch and PR, then report the PR again with a fresh assessment." and moves the job back to Implementing with a `changes:` stage event. The feedback id is claimed on `jobs.delivered_feedback_ids` before the send and given back if it fails, so a replay never sends twice. An untracked harness returns to pr once its thread settles. A gone thread is refused; close the job instead.
  - **File a follow-up** is what a failed revert offers instead, since the merged attempt's sandbox and worktree are gone. It files a new Linear issue in the configured team the way **New job** does (the factory label, plus the original job's Harness and Runs on overrides when they still apply), titled "Fix main: revert of <KEY> failed", with your text, the failed checks, the merged PR, the merge commit, why the revert failed and the revert PR. The request id keys the issue, so a retry files it once. The item then leaves the inbox (`jobs.dismissed_at`) and the audit log gets `follow_up_filed` with a link to the new issue. No runner intent is involved.
  - **Answer** posts your answer on the Linear issue as a reply (`SourceAdapter.reply`, with the panel's `LINEAR_API_KEY`) and records an `answer` intent; the runner resumes the thread as for an answer typed in Linear.
  - **Close** (`close_job`) closes the PR through the App if it is open, then fails the job the way a stop does, with your reason, and tells its thread to stop. The failure is written back to Linear once the stop settles. A failed job only has its PR closed.
  - **Retry** (`retry_job`), on a failed job, starts the next attempt without opening Linear. The runner puts the issue back where the factory label would (state Todo, label `factory` added through `SourceAdapter.requeue`) and runs the usual claim, which bumps `jobs.attempt`, so a retry is exactly what adding the label starts: a new branch (`factory/FAC-7-a2`) and a launch message that quotes the previous failure. The intent carries the failed attempt it was pressed on, so a double click or a redelivery starts one attempt, and a job that is no longer failed is left alone. If the claim can't take the job yet, for example while the failed attempt's sandbox is still held, the item says so; the label is already back on the issue, so the attempt starts when it can. The optional **note** is stored on `jobs.attempt_note` under the attempt it is for, shows in that attempt's launch message under "Owner's note for this attempt" after the previous failure, and is posted on the Linear issue as a comment (once per attempt). A later attempt ignores it.
  - **Retry stop** (`retry_stop`), on a stop that was not confirmed, asks T3 to interrupt the thread and its subagent threads again at once and gives the stop a fresh timeout.
  - **Dismiss** sets `jobs.dismissed_at` and changes nothing else; a newer failure shows again. Dismissing an unconfirmed stop says you checked the thread in T3, and lets the factory label retry the job again.
- **GitHub reviews.** A `pull_request_review` delivery from a person (not a bot, so neither Bugbot nor the factory's App) that requests changes or comments becomes a `request_changes` intent keyed `github:review:<id>`, so every delivery of one review records it once. The runner adds the review's inline comments and forwards it like the panel's request; a thread already at work only hears it. A review the job can't take yet (it has no PR recorded, waits on a question, or its sandbox won't wake) keeps the intent open: every retry looks the job up again by the intent's job, the PR URL, then the review's head branch, and moves the intent to the job's machine. A finished job, a review already sent, or a PR that is no current attempt's closes it. After 24 hours of waiting the review is dropped with a `review_dropped` audit row. An App created before this needs the **Pull request review** event enabled in its GitHub settings.

## Stopping a job

A stop ends in a verified state, not just a delivered message. Linear taking the job away (label removed, canceled, deleted) or **Close** in the inbox fails the job at once and records the stop on `jobs.stop` (`lib/stop.ts`, driven by `runner/stops.ts`):

- **States.** `requested` (recorded, nothing reached the thread yet) → `delivered` (the stop message went to the bound thread) → `escalated` (T3 was asked to interrupt) → `confirmed` or `unconfirmed`. Each step is a compare-and-set on the record, so replays, restarts and a second machine change nothing twice. The record says who asked, why, how the stop last reached the work (`message`, `interrupt`, `terminate`), the runner's last step, and the evidence it settled on.
- **Until it settles** the job keeps its launch capacity and its login slot, Linear hears nothing (no write-back, no reopen), and no new attempt starts. The board, list and run detail show **Stopping…** with the step (sending the stop, asked the agent, interrupting, ending the sandbox, waiting to confirm), and the inbox's failure line says the same.
- **A thread on this machine.** The polite message goes first; `t3 thread send` queues it behind a busy turn, so it rarely ends a long run by itself. Each tick, at most every `factory.stop.checkSeconds` (15), the runner reads the thread (`t3 thread show`) and its subagent threads at any depth (T3's MCP `t3_thread_list` with subagents; the CLI leaves them out). After `interruptAfterSeconds` (60), whatever still runs, the thread and each running subagent thread, gets T3's `t3_thread_interrupt`, one request id per run so a repeat is a no-op. Once neither the thread nor any subagent thread has an active run for `settleSeconds` (30) the stop is **confirmed**. Still running, or unreadable, `giveUpAfterMinutes` (5) after the message, it is **unconfirmed**. Archiving is no fallback: T3 refuses to archive a thread while its provider is active. Only the job's own thread and its subagent threads are ever interrupted. The waits round up to `tickSeconds`.
- **A Modal sandbox.** Teardown writes the Codex login back, ends the sandbox and runs a command in it, which must find it gone; then the stop is confirmed with that evidence. A sandbox that still answers keeps its row, and the next tick tries again.
- **No thread.** A job stopped before any thread started is confirmed at once. One with a launch in flight waits for the binding, which delivers the stop.
- **Settling.** Confirmed or unconfirmed, the source is reopened (for a Linear stop) and the failure written back (for a Close), and the capacity is free. **Stopped · confirmed** shows the evidence. **Stop not confirmed — check the thread in T3** puts the job in the inbox (`stop_unconfirmed`) with **Retry stop** and **Dismiss**, and links the thread from the card and run detail (**Open in T3**). The factory label can't retry the job until you dismiss it.
- **How the runner reaches T3** (`lib/t3-client.ts`). Starting, messaging, showing and listing threads use the `t3 thread` CLI. Subagent threads and interrupts use T3's MCP endpoint on the job's host (`server-runtime.json`'s origin, `/mcp`): `t3 auth session issue` mints a bearer session with only the scopes the call needs (`orchestration:read`, plus `orchestration:operate` to interrupt) and a 5 minute TTL, and `t3 auth session revoke` ends it after the call. The call runs on the host itself through a small script (the runner's bun here, node in a sandbox), with the token on stdin, never in argv or a log. T3 gives such a session an `approval-required` runtime-mode ceiling and refuses to interrupt a thread that runs above it (`runtime_mode_escalation_denied`), which includes the factory's `full-access` threads; the stop records the refusal and ends unconfirmed if the thread does not stop on its own. `task_cancel` only answers callers that are themselves T3 threads, so delegated subagent work is stopped by interrupting the subagent threads instead.

## Slack notifications

The runner posts a Slack message when a job lands in the [inbox](#needs-you-inbox), when the factory merges a PR on its own, and when it reverts one. It edits that same message while the item changes and once more when it is resolved (**✅ Answered**, **✅ Merged by the factory**, **↩️ Changes requested**, **🔁 Retried**, **Dismissed**, **Closed**, **✅ Stop confirmed**). The rules are in `lib/slack.ts`, the pass in `runner/slack.ts`.

- **Setup.** Create the app at [api.slack.com/apps](https://api.slack.com/apps) → **Create New App** → **From a manifest**, pick the workspace and paste:

  ```yaml
  display_information:
    name: Marshal factory
    description: Tells you when a factory job needs you.
  features:
    bot_user:
      display_name: Marshal factory
      always_online: true
    slash_commands:
      - command: /factory
        url: https://marshal-factory.vercel.app/api/slack/commands
        description: Send a job to the factory
        usage_hint: "[what to build]"
        should_escape: false
    shortcuts:
      - name: Send to factory
        type: message
        callback_id: send_to_factory
        description: File this message as a factory job
  oauth_config:
    scopes:
      bot: [chat:write, chat:write.public, im:write, commands, users:read]
  settings:
    interactivity:
      is_enabled: true
      request_url: https://marshal-factory.vercel.app/api/slack/interactions
    org_deploy_enabled: false
    socket_mode_enabled: false
    token_rotation_enabled: false
  ```

  Install it to the workspace. The interactivity URL, `https://marshal-factory.vercel.app/api/slack/interactions`, is where button clicks, modal submissions and the **Send to factory** shortcut go ([Acting from Slack](#acting-from-slack)); an app created before it needs **Interactivity & Shortcuts** turned on with that Request URL. The slash command URL, `https://marshal-factory.vercel.app/api/slack/commands`, serves `/factory` ([Filing jobs from Slack](#filing-jobs-from-slack)).
- **Environment.** Add to the runner checkout's `.env.local` and restart the runner (`bun scripts/install-runner.ts`): `SLACK_BOT_TOKEN` (**OAuth & Permissions** → Bot User OAuth Token, `xoxb-…`), `SLACK_SIGNING_SECRET` (**Basic Information** → App Credentials) and `SLACK_OWNER_USER_ID` (your member id: your Slack profile → ⋯ → **Copy member ID**). A runner without `SLACK_BOT_TOKEN` skips Slack entirely. Each runner's inventory reports whether it has the token and the member id, never their values; Settings shows **Slack connected** from that. Vercel production needs the same three for acting from Slack. Saving Settings checks only that a channel id looks like one; a channel Slack refuses shows as the runner's post error and in the test message's result. Ingest is unchanged.
- **Settings → Notifications.** **Send to** your DMs (opened with `conversations.open`), a channel by id (invite the app first if it is private; public channels work without joining thanks to `chat:write.public`), or **Off**, which posts nothing new but still resolves messages already sent. One switch per event: questions, reviews and handovers, failures, reverts (failed and done), stops not confirmed, merges by the factory. Merges you approved resolve their handover message instead of posting a new one. The settings are the one row of `notification_settings`; without a row the runner DMs you about everything. **Send test message** records a `slack_test` intent; only a runner with the token takes it, posts the test where notifications go (your DMs while they are off), and the card shows the result or Slack's error.
- **Quiet hours.** A start, an end and a time zone (an IANA name such as `Europe/Berlin`). During them only failed reverts and unconfirmed stops are sent, since main is red or an agent may still be spending. Nothing is queued: whatever still needs you when quiet hours end is posted then, and what was resolved meanwhile is never posted. Edits to messages already sent don't notify, so they go out anytime.
- **One message per event.** Each event has an id from its job, attempt, kind and stage report (`lib/slack.ts` `eventId`), the key of its `slack_messages` row with the channel and `ts`. The runner inserts the row as `posting` before it posts, so a re-tick, a restart or a second runner never posts twice; a row a dead runner left `posting` for 5 minutes is posted again. A new question or a new failure on the same job is a new event and a new message. An event older than 24 hours when the runner first sees it stays in the panel only, so turning Slack on doesn't post the backlog.
- **The pass.** The runner's own queue step after every tick, so a slow Slack holds up nothing: resolve messages whose event went away, edit open ones whose content changed (a hash of the message is kept), then post new ones. At most 25 Slack calls a pass, one at a time with a second between them. A 429 waits out a short `Retry-After` and pauses Slack for this runner for a long one; a refused post (a bad channel, a revoked token) ends the pass's posting, and every failure is in the step's log line, never thrown.
- **What a message holds.** A header `<emoji> <KEY> · <title>`, the inbox's one-line reason, repo · harness · spend, the actions the inbox offers for that kind while it is open ([Acting from Slack](#acting-from-slack)), and link buttons: **Open in panel** (`/inbox?job=<KEY>`), the pull request and the Linear issue. Text is clipped, and anything shaped like a token, plus the value of every env variable named like a token, secret, password, key or database URL, is replaced with `[redacted]`. No logs. The actions block's id is `item:<event id>`, so a click finds its message.
- **Rollout.** [Rolling out a merge](#rolling-out-a-merge) migrates and restarts the runner; add the env variables first. Add the three env variables to the panel's Vercel env for acting from Slack.

## Acting from Slack

An open message carries the inbox's actions for its kind, and each runs the panel's own owner-only inbox action (`lib/inbox-actions.ts`): the same checks, the same intents, the same runner paths, so a merge from Slack goes through the one merge service like an approval in the panel. The handler is `lib/slack-interactions.ts`, behind `app/api/slack/interactions/route.ts`.

- **Buttons.** Ready for your review: **Approve and merge** (Slack asks to confirm first), **Request changes** and **Close**. Question: **Answer**. Failed: **Retry**, **Close** and **Dismiss**. Revert failed: **File a follow-up** and **Dismiss**. Stop not confirmed: **Retry stop** and **Dismiss**. **Answer**, **Request changes**, **File a follow-up**, **Retry** and **Close** open a modal with a text box (the follow-up starts with the panel's suggested text, a close reason or a retry note is optional), and submitting it runs the action. Merges by the factory, reverts and resolved messages have only the links.
- **Who may act.** Every request must carry a valid `X-Slack-Signature` (v0, HMAC-SHA256 of `v0:<timestamp>:<raw body>` with `SLACK_SIGNING_SECRET`, compared in constant time) and a timestamp at most 5 minutes off; anything else gets a 401 before the body is read. Only the Slack user `SLACK_OWNER_USER_ID` may act; anyone else gets an ephemeral "Only the factory owner can act from Slack." The action runs as the first address in `FACTORY_OWNER_EMAILS`, so the audit log names you as it does for the panel. The proxy lets `/api/slack/*` through without a session; the signature is the check.
- **What a click does.** Slack wants an answer within 3 seconds, so the route acks and works after the response (`after` from `next/server`). The message turns pending at once without its action buttons (**⏳ Merging…**, **⏳ Sending your changes…**, **Answer sent**, **Dismissed**, …), then the route follows the intent for up to 50 seconds the way the panel's detail pane does. When the runner refuses (a red check, a moved head, a gone thread) or the action fails, the buttons come back and you get an ephemeral note with the reason, redacted, never a stack trace. Otherwise the notifier edits the message to its resolution as before. A refusal that arrives after those 50 seconds leaves the message pending until its event changes; the panel shows it.
- **Once only.** The request id is derived from the event id and the action, so a double click, a second modal or a retry records one intent, files one follow-up and posts one answer. Once the runner refused an attempt, the next click derives a new id from the refused one, so the action can be tried again, still once per double click. A button on an event that is no longer open (resolved, or replaced by a newer report) replies "This is already resolved; nothing was done." and does nothing; a modal left open on one says so when submitted.

## Filing jobs from Slack

Slack is one more front door to the panel's **New job**: `/factory` and the **Send to factory** message shortcut open the same form as a modal, and submitting it runs the panel's own `createJob` (`lib/new-job.ts`) as the owner, so the job is a Linear issue in the factory team with the factory label and the Harness, Runs on and Repository labels, claimed like any other. The handler is `lib/slack-new-job.ts`, behind `app/api/slack/commands/route.ts` and the interactivity route.

- **`/factory`.** With no text it opens the empty form. `/factory <what to build>` opens it with the first line as the title and the whole text as the description (a one-line text is the title only). `/factory help` answers with the usage. Only `SLACK_OWNER_USER_ID` gets the form; anyone else gets "Only the factory owner can act from Slack." The route checks the signature exactly as the interactivity route does (`lib/slack-request.ts` is shared), answers within Slack's 3 seconds and opens the modal after the response.
- **Send to factory.** A message's ⋯ menu → **Send to factory** opens the form with a short title from the message's first line and the message as the description, ending with `From Slack: <permalink>` (`chat.getPermalink`; without it the description is just the message). The shortcut's payload carries the message text, so no history scope is needed.
- **The form.** Title, description, repository (the enabled registered repositories, the default preselected) and harness and runs on (**Settings default** preselected, plus the enabled harnesses the machines report and Local or Modal), as in the panel. An invalid title or description is refused inline while the modal is open. A valid one closes the modal and is filed right after; the owner gets an ephemeral note where the form was opened (a DM when that fails) with the key, **Open the issue** and **Open the board**, or the reason it could not be filed. A shortcut job is also answered in the message's thread with "Filed as FAC-123" and the link, when the bot may post there; when it may not (a private channel it isn't in, someone else's DM), the job is still filed and the failure is only logged.
- **Once only.** The request id is derived from the modal's view id, and the source files one issue per request id (Linear's issue id is derived from it), so a submission Slack retries files one job.
- **Slack app settings.** For an app created from an older manifest: **Slash Commands** → create `/factory` with the Request URL `https://marshal-factory.vercel.app/api/slack/commands`; **Interactivity & Shortcuts** → **Create New Shortcut** → **On messages**, name **Send to factory**, callback id `send_to_factory`; **OAuth & Permissions** → bot scope `commands` (with `chat:write`, `chat:write.public` and `im:write` already there). `chat.getPermalink` needs no scope. Reinstall the app after adding a scope. The panel's Vercel env needs `SLACK_BOT_TOKEN`, `SLACK_SIGNING_SECRET`, `SLACK_OWNER_USER_ID` and `LINEAR_API_KEY`, as for acting from Slack and the panel's New job.

## Panel access and deploys

- **Sign-in.** Neon Auth (`auth: true` in `neon.ts`) holds the users. `proxy.ts` sends a request without a session to `/auth/sign-in`, answers `/api/*` with 401 (but `/api/slack/*`, which checks Slack's signature instead), and shows a 403 page to any account that is not the owner. The owner is an account whose email is in `FACTORY_OWNER_EMAILS` (comma-separated, case-insensitive) and verified. An unset or empty list admits nobody. `lib/live-queries.ts` checks the owner again before it seals a query, so only the owner ever holds a Realtime credential.
- **Owner account.** Sign-up stays off, and an email counts only after its owner enters the code Neon Auth mails. To create the owner on `main`:
  1. Turn on sign-up with code verification: `neon neon-auth config email-password update --branch main --enabled --email-verification-method otp --require-email-verification --send-verification-email-on-sign-up --send-verification-email-on-sign-in --auto-sign-in-after-verification --disable-sign-up false`.
  2. Trust the panel's origin, or sign-up fails with "Invalid origin": `neon neon-auth domain add https://<your panel domain> --branch main`, for example `https://marshal-factory.vercel.app`.
  3. Open `/auth/sign-up` on the panel and create the account with an address from `FACTORY_OWNER_EMAILS`.
  4. Enter the 6-digit code from the email (sender `auth@mail.myneon.app`, valid 15 minutes). The panel signs you in and opens **Jobs**.
  5. Turn sign-up off again: `neon neon-auth config email-password update --branch main --disable-sign-up true`.

  An account that signs in before it is verified gets a new code on the sign-in page.
- **Environment.** The panel needs `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `NEON_AUTH_BASE_URL`, `NEON_AUTH_COOKIE_SECRET` (`openssl rand -base64 32`), `NEON_REALTIME_URL`, `NEXT_PUBLIC_NEON_REALTIME_URL`, `NEON_REALTIME_SECRET` and `FACTORY_OWNER_EMAILS`. `next build` fails without the cookie secret. A preview build needs none of the three Realtime variables.
- **Realtime origins.** The allowed origins are `*`, because Vercel preview URLs change per branch. The sealed query is the credential, and only the owner can get one.
- **Jobs.** `/` shows every job as a board (`?view=board`) or a list (`?view=list`); the header's switch changes the view in place and remembers it in the `jobs_view` cookie, which `/` without `?view` opens. The header's repository filter works the same way with `?repo` and the `jobs_repo` cookie ([Repositories](#repositories)). An open run adds `&run=<session>` and closing it keeps the view. The old `/list` redirects to `/?view=list`. In list view J and K walk the rows, Enter opens a run and Esc closes it.
- **Settings.** `/settings` picks the harness and model every runner starts new threads on, from the enabled harnesses the machines report. **Run jobs on** picks this Mac's T3 or a Modal sandbox per job, and lists what the runner still needs for Modal. The choice is the one row of the `settings` table; the runner reads it on each launch pass and falls back to its config. A repo's defaults on **Repositories** go over it. Each job records the provider and model it launched with. Runs on Codex show stages, and their cost once the runner has read it from Codex's session logs; runs on any other harness show neither. The quiet-run watchdog applies only to Claude Code. The **Notifications** card sets up [Slack notifications](#slack-notifications).
- **Machines.** `/machines` lists every Mac whose runner reports in, with online state computed in the browser from `last_seen_at`, its resources, its T3 projects and the factory repos.
- **Vercel.** A merge to `main` deploys production, and a push to a PR branch deploys a preview. `vercel.json` migrates before `bun run build`, so production migrates the production branch and each preview migrates its own Neon branch, and runs functions in `fra1` next to the database. `scripts/migrate-guard.ts` runs first and stops a non-production build whose `DATABASE_URL` or `DATABASE_URL_UNPOOLED` points at the production branch (`PRODUCTION_ENDPOINTS` in `lib/migrate-guard.ts`; add new production endpoints there). The project's Ignored Build Step, `[ -z "$DATABASE_URL" ]`, cancels a preview that has no database yet. A merge that changes the runner still needs the live checkout updated: [Rolling out a merge](#rolling-out-a-merge).
- **Previews.** A preview build (`VERCEL_ENV=preview`) shows the data from its branch but does not subscribe to Realtime, and the footer says "Live updates off in previews". Its Neon branch has no Realtime config that the build can read. Production keeps live updates.

## Rolling out a merge

`bun scripts/rollout.ts`, run in the live checkout on the runner Mac, brings it up to `origin/main` after a merge. It stops at the first step that fails and says whether the runner is stopped; fix the cause and run it again, since every step is safe to repeat.

1. **Vercel.** Waits for the `Vercel` commit status on `origin/main`'s head, the production deploy, which also migrates. A failed deploy stops the rollout.
2. **Jobs in flight.** Refuses while this machine has a job in `queued` through `verifying` or a stop pending, counted as the runner counts them. `--wait` waits for them instead (up to six hours). It counts again after stopping the runner, and starts it again if a job was claimed in between.
3. **Pull.** Stops the runner (`bun scripts/install-runner.ts --uninstall`), then `git pull --ff-only` and `bun install`. The checkout must be on `main` with no uncommitted changes.
4. **Migrate.** `bun run db:migrate`; it changes nothing when Vercel already migrated.
5. **Ingest.** Redeploys the ingest Function (`neon functions deploy ingest --branch main --src functions/ingest/index.ts`) when a file its bundle is built from changed since the last rollout. Bun's metafile names those files, so a change to anything `functions/ingest/index.ts` imports counts, and a dependency counts through `bun.lock` or `package.json`. With no rollout recorded it deploys.
6. **Image.** Rebuilds the sandbox image (`bun scripts/sandbox-image.ts`) when `imageProblem` in `lib/sandbox.ts` reports a pin or playbook drift, or when a file the image's hook and MCP bundles are built from, or the build itself (`scripts/sandbox-image.ts`, `lib/sandbox-image-build.ts`), changed since the commit the image was built from. A machine that never built an image skips it.
7. **Runner.** Reinstalls the runner and reads `~/Library/Logs/marshal-factory/runner.log` from the restart on. It passes at the first `tick` after `start` when neither that tick nor the startup `reconcile` has a step that returned an error, and no step logged `:error` in between. A second `start` (a crash) fails it. It waits up to 15 minutes.

Steps 4 to 7 run in a new process from the pulled checkout, so a change to the rollout itself applies to the rollout that pulls it. The commit it finished with goes to `~/.config/marshal-factory/rollout.json`, which step 5 compares against next time. A commit that is already recorded and checked out exits at once; `--force` rolls it out again. `--checkout <path>` names the live checkout when the script runs from another one.

The order matters: a pin change without a rebuild leaves Modal jobs queued until the image matches, and an ingest older than the runner answers 400 to new event kinds, which the outbox sets aside. Steps the script does not cover stay by hand: env variables in Vercel or the runner's `.env.local`, and `bun scripts/install-target.ts <repo>` for a playbook change in wired repos.

- **Canary.** `bun scripts/canary.ts` (or `bun scripts/rollout.ts --canary` after the rollout) files one fixed ticket on `ski043/factory-playground` (`--repo` picks another) and follows its job. The ticket asks for a static `demo/index.html` page, served on localhost, opened and screenshotted with the `playwright` browser, verified with `factory-verify`, and a PR. It runs on Modal (the **Runs on** label) and carries the `review` label, a hard limit on the merge decision, so its PR is handed over and never merges, even on a repo set to auto. It passes when the job ran in a sandbox, its PR is open, the `pr` report attached at least one screenshot, the agent's evidence at the PR head is clean with every check passed, and the decision handed over. It fails at once when the job fails, asks a question or merges, and after `--timeout-minutes` (60) otherwise. The PR and the Linear issue stay open; close both once you have looked.

## Testing

`bun run test:regressions` runs every `scripts/*-regressions.ts` against a Neon branch it creates from production for that run, and deletes the branch when the run ends. The branch expires after 2 hours, so a crashed run cannot leak one. Pass a name prefix to run a subset, for example `bun run test:regressions ingest`. It needs the `neon` CLI signed in, and the project id from `.neon` or `NEON_PROJECT_ID`.

Each script starts with `import "./test-guard"`, which exits before any write unless the harness started it and `DATABASE_URL` points at the harness's branch. The `.env.local` database is always refused. During a regression the real Linear client, the GitHub App, `t3 thread` commands and the deployed ingest URL throw (`lib/test-mode.ts`); tests use fakes such as `threads` in `runner/ops.ts` and `github` in `lib/github/pulls.ts`.
